1. FLUXO DE CLIENTE (PÚBLICO)
═══════════════════════════════════════════════════════════════════════════════

ANTES:
┌─────────────────────────────────────────────────────────────────┐
│ Faz Booking → Espera 30s → Pressiona F5 → Ver resultado         │
│                                                                   │
│ Se rede falha:                                                   │
│ → Erro "Falha de rede"                                           │
│ → Precisa fazer tudo de novo                                     │
└─────────────────────────────────────────────────────────────────┘

DEPOIS:
┌─────────────────────────────────────────────────────────────────┐
│ Faz Booking                                                      │
│     ↓                                                            │
│ [Polling automático a cada 5s] ← useBookingPolling               │
│     ↓                                                            │
│ Status muda? → Toast notifica → setBooking atualizado            │
│     ↓                                                            │
│ Cliente vê "Confirmado!" em tempo real                           │
│                                                                   │
│ Se rede falha:                                                   │
│ → fetchWithRetry tenta 3x automaticamente                        │
│ → Se conseguir, ninguém vê o erro                               │
│ → Se falhar na 3ª, aí mostra erro                               │
└─────────────────────────────────────────────────────────────────┘

4. TRATAMENTO DE ERRO (REQUEST HELPERS)
═══════════════════════════════════════════════════════════════════════════════

Antes: Falha de rede → Erro direto
┌──────────────────────────────────────────┐
│ fetch('/api/booking')                    │
│      ↓                                   │
│ ✗ ERRO: "Network failed"                 │
│      ↓                                   │
│ Cliente vê mensagem de erro              │
└──────────────────────────────────────────┘

Depois: Falha de rede → Retry automático
┌──────────────────────────────────────────┐
│ fetchWithRetry('/api/booking')           │
│      ↓                                   │
│ Tentativa 1: ✗ Falha                     │
│      ↓ (aguarda 1000ms)                  │
│ Tentativa 2: ✗ Falha                     │
│      ↓ (aguarda 1000ms)                  │
│ Tentativa 3: ✓ SUCESSO!                  │
│      ↓                                   │
│ Cliente nem nota a falha                 │
│                                           │
│ Se todas falharem:                       │
│ → Mostra "Sem internet. Tente mais tarde"│
└──────────────────────────────────────────┘

6. CICLO DE VIDA DO POLLING
═══════════════════════════════════════════════════════════════════════════════

┌─────────────────────────────────────────────────────────────────┐
│ Componente monta                                                 │
│      ↓                                                           │
│ useBookingPolling inicializa                                    │
│      ↓                                                           │
│ [Imediatamente] poll() executa fetch                            │
│      ↓                                                           │
│ Resultado recebido → setBooking(data)                           │
│      ↓                                                           │
│ [Cada 5000ms] setInterval tira novo poll                        │
│      ↓                                                           │
│ Se status mudou → onStatusChange callback                       │
│      ↓                                                           │
│ notificationService mostra toast                                │
│      ↓                                                           │
│ ... (continua a cada 5s)                                        │
│      ↓                                                           │
│ Componente desmonta                                              │
│      ↓                                                           │
│ clearInterval limpa o timer                                     │
│      ↓                                                           │
│ Sem memory leaks! ✓                                             │
└─────────────────────────────────────────────────────────────────┘

9. COMO TESTAR
═══════════════════════════════════════════════════════════════════════════════

Teste 1: Múltiplas abas
─────────────────────────────────────────────────────
1. Abrir /history/[id] em 2 abas
2. Em aba A, fazer F5 para simular server update
3. Aba B deve atualizar em <5s
✓ Esperado: Ambas mostram mesmo status

Teste 2: Falha de rede
─────────────────────────────────────────────────────
1. DevTools → Network → Offline
2. Cliente tenta fazer booking
3. fetchWithRetry tenta 3x
4. Após 3x, mostra erro
✓ Esperado: Não trava a app

Teste 3: Novo booking para parceiro
─────────────────────────────────────────────────────
1. Cliente faz booking
2. Parceiro está no Dashboard
3. Dashboard deve atualizar em <10s
4. Toast deve aparecer
✓ Esperado: Parceiro notificado imediatamente
